OMG4-FTGS 렌더링에 CoherentRaster가 어디에, 왜 들어갔는가

핵심은 FTGS model layer를 바꾼 것이 아니라, FTGS가 timestamp별 Gaussian splat을 만든 뒤 rasterizer layer를 하나 더 연결했다는 점입니다. 기존 gsplat.rasterization() 경로는 비교 기준으로 유지되고, CoherentRaster 경로는 같은 FtgsSplats를 rasterization_CR()로 넘겨 LKG interlaced panel target을 직접 렌더링합니다.

Overview

먼저 전체 파이프라인을 잡기

기존 FTGS 렌더링은 동적 Gaussian 모델에서 특정 시간의 splat tensor를 materialize한 뒤, 그것을 일반 gsplat rasterizer에 넣는 흐름이었습니다. CR을 넣은 뒤에도 앞단의 FTGS 계산은 동일합니다. 달라진 지점은 materialized splat을 이미지로 바꾸는 rasterization 단계입니다.

FTGS

시간 t에서 렌더링할 3D Gaussian 목록을 만드는 model layer입니다.

gsplat

기존 비교 기준입니다. 같은 splat을 단일 camera view의 RGB 이미지로 rasterize합니다.

CoherentRaster

각 panel RGB subpixel이 참조할 view를 lookup으로 고를 수 있는 CR rasterizer입니다.

LKG panel

Looking Glass처럼 RGB subpixel마다 다른 view를 배치해야 하는 interlaced display target입니다.

구분 렌더링 흐름 의미
이전 FTGS materialize() -> gsplat.rasterization() 한 camera view를 일반 3DGS 방식으로 이미지화한다.

FTGS Materialization

FTGS는 먼저 timestamp별 Gaussian을 만든다

개념

DynamicGaussians.materialize(timestamp)는 checkpoint에서 decode된 평균 위치, 시간, scale, rotation, duration, velocity, appearance codebook, MLP weight를 사용해 특정 timestamp의 splat tensor 묶음을 만듭니다. 여기서 duration과 velocity는 시간에 따른 위치/투명도 변화를, appearance codebook과 MLP는 view-dependent color/opacity를 결정하는 재료입니다. CR은 이 과정 안으로 들어가지 않습니다.

왜 중요한가

FtgsSplats는 현재 시간의 3D Gaussian 목록입니다. means는 위치, quats는 회전, scales는 크기, opacities는 투명도, colors는 색 계수입니다. FTGS 결과가 잘못되면 gsplat과 CR이 모두 같은 잘못된 입력을 받으므로, CR diff를 해석할 때는 모델 stage와 rasterizer stage를 분리해야 합니다.

Code Evidence

참조: experiment/src/lkg_experiment/omg4_ftgs/model.py

def materialize(self, timestamp: float) -> FtgsSplats:
    means_t = self.means + (t - self.times) * self.velocities
    scales = torch.exp(self.scales)
    temporal_opacity = torch.exp(-0.5 * ((t - self.times) / self.durations.exp()) ** 2)
    cont_feature = self.mlp_cont(contracted)
    shs = self.mlp_view(view_feature).reshape(-1, 47, 3).float()
    dc = self.mlp_dc(space_feature).reshape(-1, 1, 3).float()
    opacities = torch.sigmoid(self.mlp_opacity(space_feature).float())
    colors = torch.cat([dc, shs], dim=1)
    return FtgsSplats(means_t, quats, scales, opacities, colors, sh_degree)

확인할 것

FTGS 원본 경로는 OMG4/OMG4_FTGS/render.py에서 같은 종류의 dynamic Gaussian을 timestamp별로 만들고 rasterizer에 넘기는 구조입니다. 현재 실험 코드는 이 과정을 FtgsSplats dataclass로 명시해 이후 backend 교체 지점을 분명하게 만들었습니다.

CR 경로를 추가하면 결과 차이가 FTGS materialization 때문인지, CR lookup/view mapping 때문인지 헷갈릴 수 있습니다. baseline gsplat output을 유지하면 같은 FtgsSplats에 대해 rasterizer만 바꾼 비교가 가능합니다.

CoherentRaster Injection

CR은 FTGS 뒤의 rasterization backend로 주입된다

CR 주입 지점은 FTGS checkpoint decode나 MLP 내부가 아닙니다. FTGS가 만든 FtgsSplats를 소비하는 별도 renderer 함수가 생겼고, 그 함수가 gsplat.rendering_coherent_raster.rasterization_CR를 호출합니다.

왜 수정했나

single-view CR은 먼저 “CR kernel이 FTGS splat 입력을 받을 수 있는가”를 검증하는 단계입니다. viewpoint_index[y, x, c] = 0으로 두면 panel의 (x, y) pixel 중 c번째 RGB subpixel이 모두 같은 view 0을 가리키므로, LKG interlacing 없이도 CR path 자체를 baseline과 비교할 수 있습니다.

Single-View vs Interlaced CR

검증용 CR과 실제 LKG panel CR은 lookup 의미가 다르다

single-view CR은 모든 subpixel이 view 0을 사용합니다. interlaced CR은 panel 해상도 HxWx3 viewpoint index를 읽고, 각 RGB subpixel이 어떤 adjacent view를 표시해야 하는지 CUDA kernel에 알려줍니다.

HxWx3 viewpoint index를 읽는 법

H와 W는 panel pixel height/width이고, 마지막 3은 RGB subpixel channel입니다. viewpoint_index[y, x, c] = v는 panel의 (x, y) 위치에서 c번째 subpixel이 adjacent view v를 사용한다는 뜻입니다. adjacent view는 source camera 주변에 합성한 근접 시점입니다. 이것은 RGB 이미지 3장을 의미하는 것이 아니라, 한 panel 이미지 안의 subpixel별 view assignment입니다. interlaced CR은 여러 view를 full image로 모두 렌더링한 뒤 섞지 않고, subpixel별로 필요한 view를 골라 바로 blend합니다.

CUDA Contract

CR CUDA kernel이 추가로 요구하는 계약

기존 gsplat은 한 view의 pixel grid를 기준으로 Gaussian을 alpha blend합니다. CR은 interlaced panel을 직접 만들기 때문에 subpixel thread마다 “어느 view를 볼 것인가”와 “원래 panel 좌표가 어디인가”를 알아야 합니다.

CPU lookup이 CUDA 입력이 되는 순서

먼저 panel-sized viewpoint_index[y, x, c]가 만들어집니다. 다음으로 CR helper가 이를 CUDA tile/thread 순서에 맞게 patchify/remap해서 view_idx_matrix와 subpixel_coord_matrix를 만듭니다. 마지막으로 kernel thread가 이 두 tensor를 읽어 “어떤 view를 blend할지”와 “결과를 원래 panel의 어느 (channel, y, x)에 쓸지”를 결정합니다.

입력 shape / 역할 왜 필요한가
view_idx_matrix [n_tile_h, n_tile_w, 3, tile_size, tile_size] 각 tile/subpixel thread가 사용할 view number를 지정한다.
subpixel_coord_matrix [n_tile_h, n_tile_w, 3, tile_size, tile_size, 3] remap 후에도 결과를 원래 channel/y/x 위치에 저장하게 한다.
translation_values [n_gauss, n_view_group, view_group_size, 2] Python 호출부의 직접 인자라기보다 CR projection 단계가 만든 내부 kernel 입력이다. reference view projection에서 adjacent view projection으로 이동할 x/y offset을 담는다.
isect_offsets, flatten_ids tile별 Gaussian intersection range 각 tile/view group에서 blend할 Gaussian list 범위를 찾는다.
CUDA kernel에서 쓰이는 방식

참조: rtgs-coherent-raster/modified-files/gsplat/cuda/csrc/CoherentRaster_CRKernel.cu

uint32_t original_x = subpixel_coord_matrix[tile_y][tile_x][channel][ty][tx][2];
uint32_t original_y = subpixel_coord_matrix[tile_y][tile_x][channel][ty][tx][1];
uint32_t original_z = subpixel_coord_matrix[tile_y][tile_x][channel][ty][tx][0];
uint32_t view_number = view_idx_matrix[tile_y][tile_x][channel][ty][tx];
uint32_t view_group_idx = view_number / view_group_size;
uint32_t view_idx_in_group = view_number % view_group_size;
float2 translation_value = translation_values[g][view_group_idx][view_idx_in_group];

핵심 해석

CR은 모든 view 이미지를 따로 렌더링한 뒤 나중에 섞는 방식이 아닙니다. target panel의 subpixel thread가 필요한 view를 선택하고, projection translation을 적용한 뒤 바로 해당 subpixel 값을 blend합니다. translation_values는 이때 reference projection을 adjacent view projection으로 보정하기 위한 per-Gaussian 2D 이동값입니다.

Recent Lookup/Timing Diff

최근 변경은 CR 수식 변경이 아니라 lookup 준비 위치 변경이다

현재 working-tree diff의 핵심은 build_cr_lookup_arrays()와 lookup_arrays_to_torch()를 render_splats_interlaced_coherent() 내부에서 매번 실행하던 구조를, CLI interlaced path에서 먼저 준비해 전달하는 구조로 바꾼 것입니다.

diff를 읽는 기준

이 변경은 CR 수식을 바꾸지 않습니다. 바뀐 것은 호출 위치와 측정 경계입니다. viewpoint_index_ms는 panel map 생성/로드 시간, lookup_cpu_ms와 lookup_h2d_ms는 CR tile layout 변환과 GPU 전송 시간입니다. 이 setup 비용은 버리는 것이 아니라 first-frame latency로 따로 보고합니다.

Before: render 내부에서 lookup 생성
lookup = build_cr_lookup_arrays(viewpoint_index, tile_size=tile_size)
view_idx_matrix, subpixel_coord_matrix = lookup_arrays_to_torch(lookup, device=device)
colors, _alpha, _meta = rasterization_CR(...)
After: CLI에서 prebuilt tensor 전달
viewpoint_index_ms = time(build_or_load_viewpoint_index(...))
prepared_lookup = prepare_cr_lookup_tensors(viewpoint_index, device=device, tile_size=tile_size)
materialize_ms = time(dynamic_model.materialize(timestamp))
view_setup_ms = time(synthesize_interlaced_viewmats(...))
cr_render_ms = time(render_splats_interlaced_coherent(
    view_idx_matrix=prepared_lookup.view_idx_matrix,
    subpixel_coord_matrix=prepared_lookup.subpixel_coord_matrix,
    return_meta=True, return_timing=True,
))
frame_ms_excluding_lookup = materialize_ms + view_setup_ms + cr_render_ms
frame_ms_including_lookup = frame_ms_excluding_lookup + viewpoint_index_ms + lookup_cpu_ms + lookup_h2d_ms

참조: render.py::PreparedCrLookup, cli.py::_render_interlaced

@dataclass(frozen=True)
class PreparedCrLookup:
    view_idx_matrix: Any
    subpixel_coord_matrix: Any
    lookup_cpu_ms: float
    lookup_h2d_ms: float

"materialize_ms": dynamic FTGS splat 생성 시간
"viewpoint_index_ms": panel viewpoint map 생성/로드 시간
"view_setup_ms": source camera, orbit center, adjacent viewmat, panel K 준비 시간
"cr_render_ms": rasterization_CR + unpatchify/unpad 시간
"frame_ms_excluding_lookup": materialize_ms + view_setup_ms + cr_render_ms
"frame_ms_including_lookup": frame_ms_excluding_lookup + viewpoint_index_ms + lookup_cpu_ms + lookup_h2d_ms
"cr_core_ms": cr_projection_ms + cr_keygen_ms + cr_sort_ms + cr_blend_ms

왜 수정했나

LKG viewpoint index를 tile layout으로 patchify/remap하고 GPU tensor로 옮기는 비용은 panel 설정이 같으면 재사용 가능한 준비 비용입니다. 이 비용을 render timer 안에 넣으면 rasterization_CR 자체가 느린 것처럼 보입니다. 그래서 first-frame cost와 steady-state dynamic render cost를 분리했습니다. 여기서 steady-state dynamic render는 dynamic_model.materialize()로 timestamp별 splat을 만드는 시간과 source camera로부터 adjacent view matrix를 준비하는 시간, 그리고 rasterization_CR 호출 시간을 함께 포함합니다. PNG 저장과 CPU 파일 I/O는 논문용 렌더링 FPS에서는 제외합니다.

Timing Interpretation

어떤 시간을 비교해야 하는가

측정값은 목적에 따라 다르게 읽어야 합니다. 한 장만 렌더링하는 비용을 보려면 lookup 포함 값을, 같은 panel map을 재사용하는 video/interactive 상황을 보려면 lookup 제외 값을 봐야 합니다. 수정 후 lookup 제외 값은 정적인 splat만 그린 시간이 아니라 dynamic materialization, adjacent view setup, CR render/post를 포함한 전체 동적 프레임 비용입니다.

아래 수치는 lookup 포함 측정이 CR core render처럼 보이던 이전 manifest를 분해해 설명하기 위한 예시입니다. 논문 표에는 동일 scene/resolution/repetition 조건에서 생성한 summary/manifest의 frame_ms_excluding_lookup과 frame_ms_including_lookup을 분리해 사용합니다.

Final Takeaway

최종 요약

FTGS는 timestamp-specific Gaussian splat을 만드는 모델 stage입니다. 기존 코드는 그 splat을 gsplat.rasterization()에 넣어 단일 view 이미지를 만들었습니다. 변경된 코드는 같은 FtgsSplats를 rasterization_CR()에도 넣을 수 있게 만들고, interlaced mode에서는 view_idx_matrix, subpixel_coord_matrix, translation_values 계약을 통해 LKG panel subpixel을 직접 렌더링합니다.

최근 lookup/timing diff는 CR math를 바꾸는 변경이 아닙니다. 재사용 가능한 panel lookup 준비를 반복 프레임 측정 경계 밖으로 빼고, frame_ms_including_lookup과 frame_ms_excluding_lookup을 나누어 first-frame setup cost와 steady-state dynamic render cost를 따로 읽을 수 있게 만든 변경입니다. 논문 실험의 steady-state FPS는 materialize_ms + view_setup_ms + cr_render_ms에 해당하는 frame_ms_excluding_lookup로, first-frame latency는 여기에 viewpoint_index_ms + lookup_cpu_ms + lookup_h2d_ms를 더한 frame_ms_including_lookup로 보고해야 합니다.
