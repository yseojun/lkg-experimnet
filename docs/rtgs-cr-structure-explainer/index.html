코드 기반 렌더링 구조 해설

RTGS 렌더링에 CoherentRaster가 어디에, 어떤 계약으로 들어갔는가

이 문서는 RTGS를 모르는 독자가 기존 official RTGS render path와 현재 CoherentRaster 적용 방식을 함께 이해하도록 만든 설명입니다. 핵심은 RTGS 모델을 바꾼 것이 아니라, timestamp 하나를 골라 4D/동적 Gaussian을 3D snapshot으로 접은 뒤 그 snapshot을 CR-compatible tensor로 넘겼다는 점입니다.

RTGS official render는 기준선

official Scene, GaussianModel, camera, timestamp, CUDA renderer 흐름을 보존해 baseline을 만든다.

snapshot CR 입력은 3D snapshot

materialize_rtgs_geometry()가 mean/covariance/opacity를 만들고, color는 camera center 기준으로 평가한다.

CR LKG view selection을 바꿈

viewpoint_index를 CR lookup tensor로 바꿔 subpixel별 view를 선택하고 rasterization_CR를 호출한다.

Overview

전체 흐름을 먼저 잡기

RTGS + CR을 읽을 때는 이미지 산출물을 섞어 생각하면 안 됩니다. 첫 번째 산출물은 official RTGS image입니다. 이것은 checkpoint, config, camera, timestamp, background, original renderer가 맞는지 확인하는 기준선입니다. 두 번째는 snapshot을 CR로 렌더한 single-view image입니다. 이것은 RTGS tensor가 CR API를 통과할 수 있는지 확인합니다. 세 번째는 LKG interlaced panel image입니다. 이것은 RGB subpixel마다 어떤 view를 보여줄지까지 포함한 최종 display target입니다.

3DGS Basics

GS 렌더링을 이해하기 위한 최소 개념

3D Gaussian Splatting은 장면을 많은 작은 3D Gaussian으로 표현합니다. 하나의 Gaussian은 카메라에 투영되면 화면 위의 타원형 footprint가 되고, 그 영역의 pixel에 color와 alpha를 기여합니다. rasterizer는 camera에서 가까운 순서와 tile별 Gaussian 목록을 이용해 여러 Gaussian의 기여를 front-to-back alpha blending으로 누적합니다.

Gaussian 하나가 하는 일

3D center가 2D 위치로 투영되고, covariance나 scale/rotation이 화면 위 footprint 크기와 모양을 만든다.

pixel color가 생기는 방식

여러 Gaussian이 같은 pixel을 덮으면 opacity가 높은 앞쪽 Gaussian부터 색이 섞인다.

tensor / term 초심자용 의미 CR에서의 역할
means Gaussian center positions 각 view에서 2D 위치로 projection된다.
covars, scales, quats shape and orientation 화면 위 ellipse footprint와 blending weight 계산에 쓰인다.
opacities how strongly each Gaussian contributes alpha blending에서 투명도를 정한다.
colors / SH color coefficients or evaluated RGB RTGS에서는 view/time에 따라 평가될 수 있어 고정 RGB라고 보면 안 된다.
rasterizer projects, sorts, and blends official RTGS는 RTGS CUDA rasterizer, CR path는 rasterization_CR를 쓴다.

RTGS Dynamics

RTGS는 timestamp마다 3DGS 상태가 달라진다

gaussian_dim=4인 RTGS는 시간 관련 파라미터를 저장합니다. timestamp t에서 opacity는 marginal_t로 조정되고, rot_4d가 켜져 있으면 mean/covariance도 시간 조건으로 바뀝니다. color는 view-dependent이며, 4D SH를 쓰면 timestamp에도 의존할 수 있습니다.

Code Evidence: dynamic geometry and color

참조: experiment/src/lkg_experiment/rtgs_coherent/cli.py

if pc.rot_4d:
    covars, delta_mean = pc.get_current_covariance_and_mean_offset(scaling_modifier, timestamp)
    means = pc.get_xyz + delta_mean

if pc.gaussian_dim == 4:
    marginal_t = pc.get_marginal_t(timestamp, scaling_modifier).reshape(-1)
    opacity = opacity * marginal_t
    mask = marginal_t > 0.05

rgb = eval_shfs_4d(active_sh_degree, active_sh_degree_t, shs_view, dir_pp, dir_t, duration)

왜 snapshot이 필요한가

CoherentRaster는 static 3DGS에 가까운 tensor 계약을 받습니다. 그래서 RTGS 4D Gaussian을 그대로 CR에 넣는 것이 아니라, 특정 timestamp에서 렌더링할 3D Gaussian 목록으로 먼저 접어야 합니다. 이 과정을 이 문서에서는 timestamp-specific snapshot 또는 materialize 단계라고 부릅니다.

Camera Contract

카메라 계약: official RTGS와 gsplat/CR 사이의 번역

official RTGS는 RTGS camera object의 world_view_transform, full_proj_transform, FoV, timestamp 등을 사용합니다. CR adapter는 같은 camera contract를 gsplat-style viewmat과 K로 바꿉니다. 이 번역이 틀리면 CR image가 나빠 보여도 원인은 CR kernel이 아니라 projection convention일 수 있습니다.

항목 official RTGS CR adapter
camera matrix world_view_transform, full_proj_transform rtgs_camera_to_gsplat_inputs()가 viewmat, K로 변환
dnerf style positive FoV 기반 projection FoV에서 focal length를 계산한다.
N3DV style FoVx=FoVy=-1.0 sentinel과 explicit intrinsics 사용 fl_x/fl_y/cx/cy가 positive이면 explicit intrinsics가 우선한다.
projection adapter original RTGS convention을 유지한다. single/compose는 Python mean/K adapter, one-shot은 CUDA rtgs_projection_adapter를 사용한다.

N3DV sentinel을 잘못 읽으면 생기는 문제

FoVx=FoVy=-1.0은 잘못된 camera 값이라고 단정하면 안 됩니다. N3DV에서는 explicit intrinsics를 쓰기 위한 sentinel contract입니다. acceptance path에서는 FoV를 임의로 positive 값으로 normalize하지 않고, 필요한 경우 RTGS-compatible projection adapter를 적용합니다.

왜 official baseline이 필요한가

CR output이 나빠졌을 때 가장 먼저 분리할 것은 RTGS loading/camera/timestamp 문제입니다. official baseline이 맞아야 snapshot reference와 CR 결과를 의미 있게 비교할 수 있습니다.

Snapshot Materialization

CR로 넘기기 전: timestamp snapshot 만들기

materialization은 시간 t를 하나 고른 뒤, 4D/동적 Gaussian을 그 순간의 3D Gaussian 목록으로 접는 과정입니다. snapshot path는 이 결과를 RtgsSnapshot으로 묶고, CR은 이 snapshot의 tensor들을 입력으로 받습니다.

snapshot field shape 설명
means [N,3] timestamp-conditioned center. rot_4d이면 mean offset이 반영된다.
covars [N,6] timestamp-conditioned 3D covariance. CR path는 covariance를 직접 넘긴다.
opacities [N] base opacity에 marginal_t를 곱한 뒤 active mask가 적용된다.
colors [N,3] or [C,N,3] single view는 한 camera center, one-shot cluster는 representative camera centers 기준으로 평가한다.
mask [N_total] marginal_t > 0.05로 살아남은 Gaussian을 기록한다.
Code Evidence: snapshot adapter

참조: cli.py::materialize_rtgs_snapshot, cr_1view.py::SnapshotGaussianProxy

geometry = materialize_rtgs_geometry(pc, timestamp=timestamp)
colors = evaluate_rtgs_colors(
    pc,
    timestamp=timestamp,
    camera_center=camera_center,
    mask=geometry.mask,
    means_for_color=geometry.means,
)
snapshot = RtgsSnapshot(geometry.means, geometry.covars, geometry.opacities, colors, geometry.mask)

snapshot과 official 차이를 먼저 분리하기

snapshot reference가 official RTGS image와 다르면 그 차이는 temporal covariance, opacity mask, SH/4D SH color, camera convention 중 하나에서 생겼을 수 있습니다. 이 차이를 바로 CR 오류라고 해석하면 디버깅 순서가 꼬입니다.

CR 1-View Ladder

1-view CR 검증: official -> snapshot -> CR

1-view CR은 LKG interlacing을 아직 넣지 않은 adapter 검증입니다. viewpoint_index를 모두 0으로 만들면 모든 RGB subpixel이 view 0을 선택합니다. 그래서 이 단계는 "RTGS snapshot이 CR renderer를 통과해 같은 camera view를 만들 수 있는가"를 봅니다.

LKG Lookup

LKG viewpoint lookup과 remapping

LKG panel output은 일반 RGB image와 다릅니다. panel의 한 pixel 안에서도 red, green, blue subpixel이 서로 다른 view를 참조할 수 있습니다. raw map은 viewpoint_index[y, x, c] = v로 읽습니다.

작은 예시

panel pixel (10, 20)
  red subpixel   -> view 12
  green subpixel -> view 13
  blue subpixel  -> view 13
raw HxWx3 view map
pad to tile multiple
patchify to [tile_h,tile_w,3,tile_size,tile_size]
optional stable remap by view id
preserve original channel/y/x through subpixel_coord_matrix
CR lookup tensor shape / role 오해 방지
view_idx_matrix [tile_h,tile_w,3,tile_size,tile_size]; thread가 사용할 view id view assignment 자체를 담는다.
subpixel_coord_matrix [tile_h,tile_w,3,tile_size,tile_size,3]; original channel/y/x remapping 후에도 결과가 원래 subpixel 좌표로 돌아가게 한다.
remapping tile 내부 subpixel 처리 순서를 view id 기준으로 정렬 view id를 바꾸는 것이 아니라 memory/coherence를 위한 처리 순서 변경이다.

참조: coherent_gsplat_bridge.py::build_cr_lookup_arrays

66-View Compose

66-view compose 경로: correctness bridge

compose path는 66개 synthetic view를 각각 single-view CR로 렌더한 뒤, viewpoint_index가 선택한 subpixel만 final panel에 복사합니다. sampled full-frame view를 official RTGS synthetic view와 비교할 수 있어 correctness bridge로 유용합니다.

compose path
for view_id in range(source_view_count):
    synthetic_camera = synthetic_camera_from_viewmat_preserving_rtgs_contract(...)
    colors = evaluate_rtgs_colors(..., camera_center=synthetic_camera.camera_center)
    cr_image = render_rtgs_coherent(...)
    accumulate_interlaced_view(interlaced, cr_image, viewpoint_index_t, view_id=view_id)
해석 기준

compose는 correctness bridge이고, one-shot이 CR식 실행 모델입니다. 66개 view를 각각 렌더하므로 CoherentRaster 논문식 one-shot 성능으로 해석하면 안 됩니다.

One-Shot CR

one-shot CR: interlaced panel을 한 번의 CR 호출로 만들기

one-shot CR은 모든 view별 full image를 먼저 만들고 섞는 방식이 아닙니다. grouped/reference-view projection과 lookup tensor를 사용해 interlaced target을 한 CR 경로에서 만듭니다. 현재 experiment runner의 user-facing engine 이름도 one_shot입니다.

materialize RTGS geometry once per timestamp
synthesize grouped adjacent_viewmats [C,S,4,4]
evaluate color at cluster representative camera centers
crop panel lookup to content viewport
call rasterization_CR() once
unpatchify, unpad, paste viewport into panel

clustered color reuse

RTGS color는 view-dependent입니다. cluster_size=1이면 view마다 color를 평가하므로 correctness reference로 쓰기 좋습니다. cluster_size>1에서는 cluster representative view의 color를 재사용하므로 품질과 속도 사이의 trade-off가 생깁니다.

CUDA Contract

CR CUDA 계약

CUDA 쪽은 reference view projection, adjacent view translation, subpixel view selection을 함께 사용합니다. translation_values는 Gaussian별, view별 2D projection offset이고, view_idx_matrix와 subpixel_coord_matrix는 각 thread가 어떤 view를 보고 어디에 결과를 써야 하는지 알려줍니다.

input role
adjacent_viewmats [C,S,4,4] anchor/source view 주변의 grouped views
view_idx_matrix tile/subpixel thread가 사용할 view id
subpixel_coord_matrix remapping 후에도 원래 output channel/y/x를 찾기 위한 좌표
translation_values reference projection에서 adjacent view projection으로 이동하는 per-Gaussian 2D offset
rtgs_projection_adapter [6] N3DV sentinel-FoV projection compensation을 위한 optional CUDA input

Timing And Metrics

timing과 metric을 어떻게 읽을 것인가

RTGS + CR timing은 static 3DGS CR timing보다 단계가 많습니다. RTGS dynamic snapshot을 만들고, color를 평가하고, CR core를 실행한 뒤, LKG panel tensor로 후처리합니다. 그래서 metrics row를 읽을 때 dynamic RTGS 비용과 CR core 비용을 분리해야 합니다.

metric group fields 의미
RTGS dynamic timing dynamic_geometry_ms, temporal_opacity_ms, snapshot_compaction_ms, dynamic_color_ms timestamp snapshot과 representative-view color를 준비하는 비용
CR core timing cr_projection_ms, cr_keygen_ms, cr_sort_ms, cr_offset_ms, cr_blend_ms CR projection, intersection/key/sort/offset, alpha blending 비용
LKG post timing lkg_unpatchify_ms, lkg_unpad_ms, lkg_panel_paste_ms patchified CR output을 panel image로 되돌리는 비용
aggregate frame_ms_without_lkg, frame_ms_with_lkg_interlace renderer-only 비교와 LKG-ready tensor 비교를 구분한다.

Caveats

틀리기 쉬운 해석

CR이 RTGS 모델을 바꾼 것이 아니다

CR은 RTGS가 만든 timestamp snapshot을 다른 rasterizer/backend로 렌더링한다.

snapshot 차이는 먼저 분리한다

snapshot과 official 차이는 먼저 분리해야 하며, 자동으로 CR 오류라고 볼 수 없다.

RTGS color는 고정 RGB가 아니다

RTGS color는 SH/4D SH로 view/time에 따라 평가될 수 있다.

N3DV FoV sentinel

N3DV에서는 FoV=-1이 explicit intrinsics를 쓰기 위한 sentinel contract다.

compose는 성능 모델이 아니다

compose는 correctness bridge이고, one-shot이 CR식 실행 모델이다.

shared K 계약

현재 one-shot 경로는 shared K 계약을 전제로 한다.

Takeaway

최종 요약

RTGS의 핵심은 시간, color, camera contract입니다. CoherentRaster는 그 model stage를 바꾸지 않고, timestamp snapshot을 CR-compatible tensor로 만든 뒤 rasterization/backend와 LKG subpixel view selection을 바꿉니다. 그래서 올바른 해석 순서는 official RTGS, snapshot reference, CR one-view, compose bridge, one-shot CR입니다.

구현 관점에서 중요한 경계도 명확합니다. official_1view.py는 기준선을 만들고, cli.py의 materialize 함수들은 snapshot을 만들며, cr_1view.py는 adapter를 검증합니다. cr_66views.py의 compose path는 correctness bridge이고, cr_one_shot.py와 rasterization_CR가 LKG interlaced output을 한 CR 경로에서 만드는 현재 실험 모델입니다.
